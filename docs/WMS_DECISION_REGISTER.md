# GFMS v0.3 – Warehouse Management System (WMS)
## Decision Register (`DEC-01` through `DEC-12`) & Approved Scope

**Document Status:** Consolidated & Finalized (Phase 02)  
**Mode:** Read-Only Documentation — No Implementation Performed  
**Alignment:** Garment Factory Management System (GFMS v0.3)

---

## 1. Approved Module Scope & Architectural Guardrails

The following scope boundaries are **formally approved** and govern all Phase 03+ design and implementation:

1. **Dedicated Warehouse Management Module**: Implement a standalone WMS module (`backend/src/modules/warehouse`, `frontend/src/pages/warehouse`, and dedicated `/api/warehouse/*` + `/api/inventory/*` endpoints).
2. **`DEP-INV` Remains Organizational**: Keep `departments` record `DEP-INV` (`id = 3`, *Inventory & Warehouse*) strictly as an organizational/HR department for personnel rosters and managerial hierarchy. Do **not** repurpose Department Management (`DepartmentModule` / `MyDepartmentPage`) into Warehouse inventory operations.
3. **Preserve Existing Auth & RBAC Architecture**: Extend GFMS's existing relational RBAC (`users` ↔ `user_roles` ↔ `roles` ↔ `role_permissions` ↔ `permissions`) and `authenticateJWT` middleware. Do **not** build a parallel authentication or authorization system.
4. **Preserve Existing APIs**: Existing Production Setup (`/api/production/*`), Department Management (`/api/departments/*`), Users (`/api/users/*`), and Automated Test Suite endpoints must remain backward-compatible with zero regressions.
5. **Preserve Existing Audit Infrastructure**: Integrate with the existing `AuditService.log` and `audit_logs` append-only table inside atomic database transactions alongside the new immutable inventory movement ledger.

## 2. Approved Business Decisions Register (`DEC-01` – `DEC-12`)

These 12 decisions are **final** and must not be altered without explicit System Administrator approval.

| Decision ID | Topic | Approved Choice | Detailed Specification & Rationale | Schema / Workflow Impact |
|---|---|---|---|---|
| **DEC-01** | **Storage Bin Granularity** | **B – Configurable per warehouse, with default bin** | Each `warehouse` defines `require_bin_tracking` (boolean). Every warehouse automatically receives a system `DEFAULT` location (`location_type = 'STORAGE'` / `'GENERAL'`) upon creation so warehouses operating without granular racks/bins still maintain consistent, non-null foreign keys in balances and movements, while bin-managed warehouses enforce explicit Zone/Aisle/Rack/Bin selection. | `warehouses.require_bin_tracking`; non-null `location_id` FK on `inventory_balances` and `stock_movements`; automatic default location provisioning. |
| **DEC-02** | **Fabric Roll UOM** | **A – Actual measured quantity per roll** | Fabric and roll-tracked materials record their base UOM (e.g., `meter`, `yard`, `kg`) on `materials`, while each received physical roll in `inventory_lots` captures its actual measured net quantity (`received_qty`, `remaining_qty`) rather than assuming rigid fixed-length rolls. Optional standard UOM conversion helpers may assist entry, but balances track actual measured units. | `materials.base_uom`; `inventory_lots` tracks `roll_number`, `initial_qty`, and roll-level balances in base UOM. |
| **DEC-03** | **Material Attributes** | **A – Hybrid standard columns + JSON attributes** | Core searchable/filterable properties (`sku`, `name`, `category_id`, `base_uom`, `color`, `size`, `reorder_level`, `min_stock_level`, `is_lot_tracked`, `is_roll_tracked`, `requires_qc_on_receipt`) are stored as normalized relational columns; category-specific garment properties (`GSM`, `width`, `composition`, `shrinkage_pct`, `fabric_type`, `style_code`, `carton_specs`) are stored in a structured JSON attribute payload (`attributes_json TEXT`, compatible with both PostgreSQL and `pg-mem`). | Clean SQL indexing on core attributes without schema migrations per trim/fabric type; full `pg-mem v3.0` compatibility. |
| **DEC-04** | **FIFO Enforcement** | **B – Advisory FIFO with reason-code override** | Picking suggestions sort eligible `AVAILABLE` lots/rolls in FIFO order (oldest `received_at` first, respecting shade-lot grouping). Users may select a newer lot/roll only by supplying an explicit `fifo_override_reason_code` and remarks, which are recorded on the issue transaction and audited in `audit_logs`. Hard blocking applies only to non-`AVAILABLE` stock (`QUARANTINE`, `HOLD`, `DAMAGED`, `SCRAP`). | `stock_transactions.fifo_override_reason` / notes; `AuditService.log` captures override events; FIFO remains independent from WAC valuation. |
| **DEC-05** | **QC Quarantine** | **B – Configurable by material / category** | `material_categories` and `materials` support `requires_qc_on_receipt` (material overrides category default). When `true`, accepted GRN quantities land in `stock_status = 'QUARANTINE'` with `qc_status = 'PENDING'`. When `false` (e.g., low-risk consumables/polybags), accepted quantities land directly in `AVAILABLE` (`qc_status = 'PASSED'` or exempt). | `requires_qc_on_receipt` flags on categories & materials; GRN posting routes stock into `QUARANTINE` vs `AVAILABLE` deterministically. |
| **DEC-06** | **Requisition Approval** | **A – Manager approval before issue / reservation** | Material Requisitions follow a controlled lifecycle (`DRAFT → SUBMITTED → APPROVED → PARTIALLY_ISSUED → FULFILLED`). Stock reservation (`qty_reserved`) occurs only upon Manager approval, and Warehouse Keepers can issue stock only against `APPROVED` or `PARTIALLY_ISSUED` requisitions. | `material_requisitions` status state machine; `qty_reserved` incremented atomically on approval and decremented on issue/cancel. |
| **DEC-07** | **Warehouse Transfer** | **A – Dispatch, in-transit, receive** | Inter-warehouse transfers follow a strict two-step physical custody handoff (`DRAFT → DISPATCHED (IN_TRANSIT) → RECEIVED / RECEIVED_WITH_DISCREPANCY`). Dispatch posts an `OUT` movement from source warehouse into `IN_TRANSIT` custody; destination confirmation posts an `IN` movement into target warehouse (recording shortages/transit damage explicitly). Intra-warehouse bin-to-bin moves execute as single-step atomic moves. | Two-step transfer header/lines; `IN_TRANSIT` stock state/tracking; linked `OUT` and `IN` movement rows; discrepancy resolution flow. |
| **DEC-08** | **Stock Adjustment** | **A – Threshold-based approval** | Every adjustment/write-off requires a mandatory `reason_code` and strict maker-checker segregation (submitter cannot approve own adjustment). Approvals route by configurable threshold: Warehouse Manager approves adjustments within policy threshold; Factory Manager must approve write-offs and adjustments exceeding the threshold. | `stock_adjustments` approval columns (`submitted_by`, `approved_by`, `approval_level`, `threshold_exceeded`); configurable threshold policy setting. |
| **DEC-09** | **Operational Roles** | **A – Dedicated operational roles** | Extend existing GFMS `roles` and `permissions` tables with dedicated WMS/operational roles (`Warehouse Manager`, `Warehouse Keeper`, `QC Manager`, `QC Inspector` [or combined QC role per Phase 03 seed], `Purchasing Manager`, `Production Manager`, `Finance Viewer`) alongside existing `System Administrator`, `Factory Manager`, `Department Manager`, and `Department User`. | Additive role & permission seeds in Phase 03/04; zero replacement of existing `auth.middleware.ts` RBAC engine. |
| **DEC-10** | **Reorder Approval** | **A – Warehouse Manager → Purchasing Manager → Factory Manager** | Reorder Requests follow a 3-tier review chain: Warehouse Manager initiates/submits replenishment need → Purchasing Manager reviews sourcing/vendor/lead-time → Factory Manager grants final approval (`APPROVED`), after which an external/future PO reference may be linked. | `reorder_requests` multi-stage status machine (`OPEN → SUBMITTED → PURCHASING_REVIEWED → APPROVED → LINKED_TO_PO / CLOSED`). |
| **DEC-11** | **Inventory Valuation** | **A – Weighted Average Cost** | Inventory valuation uses **Weighted Average Cost (WAC)**, calculated independently of physical FIFO picking. Incoming priced receipts update WAC; issues, transfers, and negative adjustments value stock at current WAC and record cost snapshots on `stock_movements`. WAC is an operational inventory valuation policy, not a full accounting GL module. | `unit_cost` / `total_cost` snapshots on `stock_movements`; WAC fields on material/balance cost records. |
| **DEC-12** | **Notifications** | **A – In-app notifications** | Operational alerts (low stock, pending QC quarantine, pending approvals, delayed in-transit transfers, pending requisitions) are surfaced via an in-app notification feed / alert queries and dashboard badges without requiring external SMTP/SMS/WebSocket infrastructure. | Additive `in_app_notifications` or query-driven alert endpoints + UI notification badge/panel; works offline on Windows local installs. |

## 3. Open Operational Parameters (Non-Blocking or Phase 03 Config Defaults)

While all 12 architectural decisions above are finalized, the following operational parameters should be confirmed as configurable defaults in `warehouse_settings` during Phase 03:

| Ref | Parameter | Question / Note | Default Policy Proposed for Configuration |
|---|---|---|---|
| **PARAM-01** | Adjustment Threshold Value (`DEC-08`) | Exact numeric/monetary limit distinguishing Warehouse Manager vs. Factory Manager approval (and whether all `WRITE_OFF` / `SCRAP` reasons unconditionally escalate to Factory Manager). | Store numeric threshold in configurable `warehouse_settings` (`adjustment_manager_max_value` / `adjustment_manager_max_qty`); route all `WRITE_OFF` to Factory Manager by default. |
| **PARAM-02** | WAC Costing Scope (`DEC-11`) | Whether Weighted Average Cost is computed per `(material_id)` globally across the factory or per `(warehouse_id, material_id)`. | Confirm during Phase 03 schema DDL (company-wide `material_id` WAC vs. warehouse-scoped WAC table). |
| **PARAM-03** | Over-Delivery Tolerance | Whether GRNs allow `received_qty > expected_qty` and what tolerance percentage triggers Manager warning/approval. | Configurable `grn_over_receipt_tolerance_pct` in `warehouse_settings`. |
| **PARAM-04** | Warehouse Scope Assignment | How `Warehouse Manager` / `Warehouse Keeper` users map to specific warehouses (e.g., `warehouses.manager_id` + a `warehouse_staff` / `warehouse_assignments` mapping table vs. `DEP-INV`). | Support `warehouses.manager_id` plus explicit user-warehouse scope mapping so keepers/managers are strictly scoped server-side. |
